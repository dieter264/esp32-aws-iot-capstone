# Local HTTPS OTA Test Server

This folder contains a minimal local HTTPS server setup for testing ESP32 OTA firmware updates.

The general ESP32 setup, including Wi-Fi provisioning, AP access, sensor setup, SNTP setup, build and flash instructions, is described in the [top-level project README](../README.md).

This README only describes the local OTA test server setup.

## 1. Test setup

The OTA test verifies the following path:

```text
Firmware version A running on ESP32
- firmware version B built locally
- firmware-B.bin copied to ota-server/bin/
- local HTTPS OTA server started
- ESP32 downloads firmware-B.bin via HTTPS
- OTA write succeeds
- ESP32 reboots
- firmware version B is active after reboot
```

The test setup uses:

```text
ESP32-S3 firmware
- Wi-Fi STA connection
- local HTTPS server on the development machine or VM
- TLS server certificate
- locally generated test certificate/key
- OTA binary served from ota-server/bin/
```

The OTA server runs on the development machine or VM.

**Note:** The ESP32 must be able to reach this machine over the local network.

## 2. Folder layout

Expected folder structure:

```text
ota-server/
├── README.md
├── certs/
│   ├── .gitkeep
│   ├── cert.pem
│   └── key.pem
└── bin/
    ├── .gitkeep
    └── firmware-<version>.bin
```

**Note:** The certificate files and firmware binaries are generated locally and must not be committed to Git.

## 3. Install required tools

On Ubuntu, OpenSSL is required.

```bash
sudo apt update
sudo apt install openssl
```

Check that OpenSSL is available:

```bash
openssl version
```

## 4. Create HTTPS server certificate

```bash
cd ota-server
```
Run the following commands from the `ota-server/` folder.

The `certs/` folder already exists in the repo structure.

Replace `<OTA_SERVER_IP>` with the IP address of the machine running the OTA HTTPS server.

Example IP address:

```text
192.168.178.68
```

The ESP32 OTA URL must later use the same IP address that is written into the server certificate `subjectAltName`. Otherwise TLS server certificate verification will fail.

Create a self-signed certificate and private key:

```bash
openssl req -x509 -newkey rsa:2048 -days 3650 -nodes \
  -keyout certs/key.pem \
  -out certs/cert.pem \
  -subj "/CN=<OTA_SERVER_IP>" \
  -addext "subjectAltName = IP:<OTA_SERVER_IP>"
```

This creates:

```text
certs/key.pem
certs/cert.pem
```

The HTTPS server uses:

```text
certs/cert.pem
certs/key.pem
```

The ESP32 OTA client must trust:

```text
certs/cert.pem
```

## 5. Build OTA firmware binary

Firmware binaries are generated by the normal ESP-IDF build.

### Verify flash and partition settings

The project already selects the custom partition table and 16 MB flash size through [sdkconfig.defaults](../sdkconfig.defaults). If you reuse an existing `sdkconfig`, verify these settings before building.

From the project root:

```bash
idf.py menuconfig
```

Check the following settings:

- **Partition Table > Partition Table**: select **Custom partition table CSV**.
- **Partition Table > Custom partition CSV file**: set `partitions.csv` (relative to the project root).
- **Serial flasher config > Flash size**: select **16 MB**.

Save and exit, then inspect the configured partition layout:

```bash
idf.py partition-table
```

The output should include `factory`, `ota_0`, and `ota_1`, each with a size of 4 MiB, as defined in [partitions.csv](../partitions.csv). This command checks the local build configuration; it does not read or update the partition table on the device. See the migration notes below if the device still uses the v0.1 layout.

### Build the application image

From the project root:

```bash
idf.py build
```

The project build copies the application binary to a versioned OTA filename such as:

```text
ota-server/bin/firmware-0.3.bin
```

The version is derived from `FIRMWARE_VERSION` in `firmware.hpp`.

When changing `FIRMWARE_VERSION`, a normal build is sufficient. The top-level CMake file registers `firmware.hpp` as a CMake configure dependency, so the versioned OTA binary name is updated automatically.

### Migrating from v0.1

The application partition layout changed between the public v0.1 release and v0.3:

| Application partition | v0.1 size | v0.3 size |
|---|---|---|
| `factory` | 2 MiB | 4 MiB |
| `ota_0` | 2 MiB | 4 MiB |
| `ota_1` | 2 MiB | 4 MiB |

The larger slots also change the OTA partition offsets. The current HTTPS OTA path downloads only the application image and uses the partition table already on the device. It does not install `partitions.csv` or migrate the flash layout. An application image that fits an old slot may still be usable there, but that leaves the old layout in place.

To adopt the v0.3 layout, use the ESP-IDF v6.0.1 environment, complete the [device HTTPS certificate setup](../README.md#61-create-the-devices-https-certificate), and run these commands from the project root with the board connected over USB:

```bash
idf.py build
idf.py flash monitor
```

This flashes the bootloader, partition table, initial OTA data, and application. Once the device has the v0.3 layout, use the application-only OTA workflow below for subsequent updates that keep the same layout.

Example workflow:

```text
1. Set FIRMWARE_VERSION to version A.
2. Build and flash version A.
3. Set FIRMWARE_VERSION to version B.
4. Run idf.py build.
5. Use ota-server/bin/firmware-B.bin for the OTA test.
```

## 6. Start HTTPS OTA server

The local HTTPS OTA server is started with OpenSSL.

`openssl s_server -WWW` serves files from the current working directory. Therefore, start it from the `ota-server/` folder so that files below `bin/` are available via `/bin/<filename>`.

```bash
openssl s_server \
  -accept 8443 \
  -cert certs/cert.pem \
  -key certs/key.pem \
  -WWW
```

Expected result:

```text
OpenSSL starts successfully
server listens on port 8443
files from ota-server/bin/ are served
```

If the ESP32 cannot connect, check that the server machine firewall allows incoming TCP connections on port `8443`.

Useful check:

```bash
ss -lntp | grep 8443
```

## 7. Verify OTA binary URL

The OTA URL has this form:

```text
https://<OTA_SERVER_IP>:8443/bin/firmware-<version>.bin
```

Example:

```text
https://192.168.178.68:8443/bin/firmware-0.3.bin
```

From another terminal on the development machine or VM, verify that the file is served:

```bash
curl -f -k https://192.168.178.68:8443/bin/firmware-0.3.bin -o /dev/null
```

Expect a successful transfer with curl exit status zero. The transferred size depends on the built image. The `-f` option makes HTTP errors, such as a missing binary, fail the check.

The `-k` option is only used for this local curl test because the certificate is self-signed.

The ESP32 should use certificate verification and must be configured to trust the OTA server certificate.

## 8. ESP32 OTA configuration

Configure OTA via the ESP32 HTTPS configuration page.

The general access procedure for the ESP32 configuration page is described in the top-level README.

### OTA URL

Use:

```text
https://<OTA_SERVER_IP>:8443/bin/firmware-<version>.bin
```

Example:

```text
https://192.168.178.68:8443/bin/firmware-0.3.bin
```

The OTA server IP must match the `subjectAltName` in the generated server certificate.

If the certificate was generated with:

```text
subjectAltName = IP:192.168.178.68
```

then the OTA URL must use:

```text
https://192.168.178.68:8443/bin/firmware-0.3.bin
```

Using another IP address or a hostname will cause TLS server certificate verification to fail.

### OTA server certificate

Copy the complete content of:

```text
ota-server/certs/cert.pem
```

into the ESP32 OTA server certificate configuration field.

The full PEM block is required:

```text
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
```

Save the configuration.

## 9. Run OTA update test

Recommended test procedure:

```text
1. Build and flash firmware version A.
2. Boot the ESP32 and verify that firmware metadata reports version A.
3. Change FIRMWARE_VERSION to version B.
4. Run idf.py build.
5. Confirm that ota-server/bin/ contains firmware-B.bin.
6. Start the HTTPS OTA server.
7. Configure the ESP32 OTA URL for firmware-B.bin.
8. Trigger the OTA update.
9. Wait for OTA download/write/reboot.
10. After reboot, verify that firmware metadata reports version B.
```

Expected firmware behavior:

```text
OTA update starts
HTTPS connection succeeds
firmware image is downloaded
OTA partition is written
OTA image validation succeeds
boot partition is updated
ESP32 reboots
new firmware version is active
```

## Expected result

After a successful OTA update, the ESP32 should reboot into the new firmware.

Expected result on the ESP32 status/config page:

```text
Firmware version: <new-version>
Build date/time: <new-build-time>
IDF target: esp32s3
ESP-IDF version: <idf-version>
```

Expected result in logs:

```text
OTA update completed successfully
rebooting into new firmware
firmware version after reboot matches OTA binary version
```

## Troubleshooting

### OTA URL returns 404

Likely cause:

```text
The firmware binary name in the OTA URL does not match a file in ota-server/bin/.
```

Fix:

```text
Check the exact filename in ota-server/bin/.
Check that openssl s_server was started from the ota-server/ folder.
```

### ESP32 cannot connect to OTA server

Likely causes:

```text
OTA server is not running
wrong IP address
wrong port
firewall blocks incoming TCP port 8443
ESP32 is not connected to Wi-Fi STA
```

Useful checks:

```bash
ss -lntp | grep 8443
curl -f -k https://<OTA_SERVER_IP>:8443/bin/firmware-<version>.bin -o /dev/null
```

### TLS certificate verification fails

Likely cause:

```text
The OTA URL does not match the certificate subjectAltName.
```

Example:

```text
OTA URL: https://192.168.178.68:8443/bin/firmware-0.3.bin
Certificate: subjectAltName = IP:192.168.178.68
```

These must match.

Another possible cause:

```text
The ESP32 is not configured with the correct OTA server certificate.
```

Fix:

```text
Copy the complete content of ota-server/certs/cert.pem, including BEGIN/END CERTIFICATE lines.
```

### Certificate parse error on ESP32

Likely cause:

```text
The configured certificate is malformed, incomplete, or not a PEM certificate.
```

Fix:

```text
Copy the complete PEM block again.
```

### OTA update succeeds but firmware version does not change

Likely causes:

```text
The OTA URL points to the old firmware binary.
The firmware was rebuilt without changing FIRMWARE_VERSION.
The browser/status page still shows cached data.
```

Fix:

```text
Check the exact OTA binary filename.
Check FIRMWARE_VERSION in firmware.hpp.
Run idf.py build again.
Reload the ESP32 status page after reboot.
```
